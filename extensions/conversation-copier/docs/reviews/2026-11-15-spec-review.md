# Copier 1.0 spec: independent review

**Reviewed:** spec.md draft v1, November 15, 2026
**Reviewer:** independent agent (did not write the spec)

## Summary

The direction is right: read each site's own data, one conversation model, one Markdown writer, and a completeness line in every export. The weakest part is that completeness line, which is the spec's headline promise. It has no definition for the data adapters, it counts messages only, and it will say "complete" when files failed, when content was never read, or when the walk took the wrong branch. The spec also does not say what happens to content types the mapping does not list. Under one reading a single new part type sends a 457-message chat to a 1-exchange page read. Under the other reading the content disappears without a word. Several adapter steps give wrong output on ordinary inputs: the ChatGPT marker clean-up, the Claude citation offsets, and the ZIP name dedupe inherited from 0.4.0. On the platform side, the popup and clipboard flow has gaps. Adding two Copilot hosts turns Copier off for every existing user, which costs a lot for one alias host and one untested host, and there is a no-warning alternative. The page-reading fallbacks for Claude, ChatGPT and Grok should be cut.

## Findings

### F1. "Complete" has no definition for the data adapters
- **Severity:** high
- **Where:** 3.2, 3.3, 4.1 to 4.4, 8
- **Problem:** Section 3.3 prints "complete", but no section says how a data adapter decides that. `expected` is null for Gemini, and the spec gives no wording or rule for the null case. For Claude, ChatGPT and Grok the obvious number to compare against (all messages in the data) is wrong, because the data is a tree. The live check's own ChatGPT chat had 612 nodes for 457 messages, so a node-count comparison calls a full export partial. A builder who notices this will most likely drop the comparison and print "complete" every time. Scenario 1: the Claude walk from the leaf meets a `parent_message_uuid` that is not in `chat_messages`. 0.4.0's loop just stops there, so the export is a clean-looking tail of the chat, labeled complete. Scenario 2: Gemini paging stops after page one because the token sits in a different slot than the builder assumed. The export holds 100 of 240 turns and is labeled complete.
- **Suggested fix:** Define "complete" per adapter. A tree walk is complete only when it reaches the site's root marker (verify what Claude puts in the first message's parent, the ChatGPT mapping root with a null message, a Grok node with no parent) and finds no missing parent on the way. A paged source is complete only when the last page came back with no token. Anything else prints "may be partial" with the reason. Where the site gives no total, print "N messages (all pages read; the site gives no total)" instead of "complete". Add each case to the unit tests.
- **Answer:** Accepted. Spec v2 section 3.3 defines complete per adapter, and each rule was checked live on November 15. Claude: the walk from the leaf ends at a parent id that is not in the message list and begins `00000000` (60 of 60 chats); any other missing parent prints "may be partial". ChatGPT: the walk reaches the node with a null parent and a null message (22 of 22 chats). Grok: the walk ends at the one node whose parent id is absent from the node set. Gemini: the last page came back with no cursor (forced paging: page one of 10 carried a cursor, page two held the 11th turn and none). Copilot: positions 1 to setsize all collected. Where the site gives no total, the line reads "N messages (all pages read; Gemini gives no total)". Each rule gets unit tests, including a missing parent.

### F2. Unknown content types: the strict reading and the lenient reading both lose data
- **Severity:** high
- **Where:** 4 (intro), 4.1, 4.2, 4.3
- **Problem:** Section 4 says a missing or wrong-typed field raises a format error, and the whole export then falls back to page reading. It does not say what happens to a block type, `content_type` or part type that is not in the mapping lists. Both readings fail. Strict: ChatGPT adds a content type, or a voice chat carries non-string parts inside `multimodal_text`. The parse throws, and a 457-message chat exports as the 1 exchange the page draws. Lenient: the unknown part is skipped. The message comes out empty, 0.4.0's habit is to drop empty messages (`filter(m => m.text.length > 0)`), and the header still says complete.
- **Suggested fix:** Use two error classes. Structural errors fall back or fail: no message list, no ids or parent links, a wrong top-level type. An unknown block or part type never triggers a fallback and never disappears. It renders as a one-line placeholder that names the type (for example `[unsupported content: audio_transcription]`) and keeps any string fields found inside it, and the completeness note counts it. A message is never dropped for being empty after mapping; it gets a placeholder instead.
- **Answer:** Accepted as written. Spec v2 sections 3.2 and 4 use two error classes. Structural errors (no message list, no ids or parent links, wrong top-level type) stop the export with a stated reason. An unknown block, part or content type renders as `[unsupported content: <type>]`, keeps any string fields found inside it, and is counted in the completeness note. A message is never dropped for being empty after mapping.

### F3. The completeness line counts messages only, so missing files and unread content go unreported
- **Severity:** high
- **Where:** 1, 3.2, 3.3, 3.5, 4.3 to 4.5, 6, 7
- **Problem:** Section 1 promises sources, images and files. `completeness` only counts messages. Scenario 1: 3 of 40 Claude files return 403 during Export. 0.4.0 counts the failures but shows "N messages + 37 files", and the 1.0 model has no field to carry the failures. Scenario 2: Grok images on another host become links (4.3). Since Chrome 85, a content-script fetch to another origin is held to the page's CORS rules, so the same thing can happen to Gemini images and to any ChatGPT `download_url` that is not same-origin. Section 6's "all requests are same-origin" does not hold for files. Scenario 3: the Copilot adapter reads only answer HTML (4.5), so Copilot sources, images and files are never read. Scenario 4: until the Gemini slots are decoded, Gemini thinking, sources and images are not read either. In every one of these the header says "complete".
- **Suggested fix:** Add `files: { got, failed: [name and reason] }` and `notIncluded: [text]` to the model. Each adapter sets `notIncluded` (for example "Copilot: sources, images and files are not exported"). The header and the toast print both. Each failed or link-only file gets a line in the Markdown where it belongs ("report.pdf could not be downloaded: HTTP 403"). Write the cross-origin rule once for all adapters, not only for Grok.
- **Answer:** Accepted. The model gains `files: { got, failed: [{ name, reason }] }` and `notIncluded: [text]` (spec v2 3.2). The header and toast print both. A failed or link-only file gets a line where it belongs. The cross-origin rule is written once in 3.5 for every adapter. Until a slot is decoded and verified, its content is listed in `notIncluded` (for example Gemini thinking and Copilot sources and images).

### F4. The branch choice is unverified on three sites, and nothing checks it against the screen
- **Severity:** medium
- **Where:** 2.3, 4.1, 4.2, 4.3, 4.4, 8
- **Problem:**
  - Grok: "the newest leaf by `createTime`" when `rid` is absent is a guess. The only chat checked had 6 messages and no branches. Scenario: the user edits message 3, which creates a new branch, then uses the arrows to go back to the original branch. The URL carries no `rid`, so the export writes the edited branch and labels it complete.
  - Gemini: `turn[3][0][0]` takes the first answer candidate. After a regenerate, or a pick from the drafts, the answer on screen may be a different candidate. This was not checked.
  - Claude and ChatGPT: nobody checked whether `current_leaf_message_uuid` and `current_node` follow a branch switch made with the arrows when no new message is sent.
  - Claude fallback: "index order when the leaf is missing", run on a `tree=True` response, mixes every branch together. Two answers to the same question appear back to back, the count goes up, and the export is labeled complete.
- **Suggested fix:** (1) Before building each rule, verify it on one chat per site that has both an edit and a regenerate. (2) Add a cheap runtime check: compare the last message the page shows (a normalized text prefix) with the last exported message. On a mismatch, the export says "the exported branch may differ from the one on screen". (3) Replace the index-order fallback with a walk from the newest leaf plus a note, or fail with a reason.
- **Answer:** Accepted in three parts. (1) Branch rules get a live test on a chat with an edit and a regenerate per site; creating those chats on Nikhil's accounts is an open question for him (spec v2 11). (2) The screen check is added (3.8): the normalized text prefix of the last message on screen is compared with the last exported message, and a mismatch adds "the exported branch may differ from the one on screen". (3) The index-order fallback is removed. A missing leaf on Claude walks from the newest message by `created_at` and says so. Grok checked November 15: the page URL carries `rid` after load, and it names the single leaf.

### F5. Gemini paging, account path and token lifetime are untested
- **Severity:** medium
- **Where:** 2.3, 4.4
- **Problem:** The check never paged: 11 turns fit in one page of 100. The spec says "repeat until none comes back" but not where the token sits. Section 2.3 says a token came back even for the 11-turn chat. If a token always comes back, the loop either never ends or fetches the same page again and duplicates turns. Multiple accounts: users signed into two Google accounts see chats at `/u/1/app/...`, and a request sent to `/_/BardChatUi/...` without the `/u/1` prefix probably goes to account 0 (verify). Gems live at `/gem/{gem}/{id}`. The `at` value read from the inline script at page load may be stale on a tab left open for hours.
- **Suggested fix:** Force paging with the chat you already have: page size 10 on the 11-turn chat. Stop on any of: no token, the same token twice, an empty page, or a page cap. Dedupe turns by id and reverse once, after joining all pages. Build the endpoint from the page's path prefix. On an auth error, tell the user to reload the page.
- **Answer:** Accepted. Paging was forced on November 15 with page size 10 on the 11-turn chat: page one returned 10 turns and a cursor at `data[1]`, page two returned 1 turn and no cursor, and the 11 response ids were unique. A page of 100 returned all 11 and no cursor. Stop rules (no cursor, a repeated cursor, an empty page, a page cap), dedupe by response id and one reverse after joining are in 4.4. The endpoint is built from the page path prefix so `/u/N` accounts and Gem paths work; neither was available to test, so both go in the untested list. An auth error tells the user to reload the page.

### F6. The Gemini guard is too weak to catch shifted positions
- **Severity:** medium
- **Where:** 4.4, 13 (risk 3)
- **Problem:** "If the positions do not hold strings" passes whenever any string sits at the position, and these arrays hold many strings: ids, URLs, model names, locale codes. Scenario: a client update inserts one element at the front of each turn. `turn[2][0][0]` now holds an id, the guard passes, and every "You" message in the export is an id, labeled complete. A second problem: answer text at `turn[3][0][0][1][0]` takes only the first element of what looks like an array of text parts. If Gemini ever splits an answer into two parts, the second part is dropped.
- **Suggested fix:** Anchor the guard on values with a known shape: the `c_` conversation id, the response and candidate id prefixes at their slots (verify the prefixes on live data), and a time value that is a number in a sane range. Join every string in the answer text array, and add a fixture with two parts.
- **Answer:** Accepted. Prefixes checked live on November 15: `turn[0]` holds `c_` and `r_` ids, `turn[1]` holds `c_`, `r_` and `rc_`, and the candidate's first element is an `rc_` id. The guard anchors on those three, plus a numeric time in a sane range. Answer text joins every string in the text array (11 of 11 turns had one part; a two-part fixture is added).
  - **Later note (November 15, probe run on all 7 Gemini chats):** `turn[1]` is the parent turn's ids, missing or blank on the first turn, so the guard no longer requires it. It now feeds a parent-link check instead: 17 links, none broken. The guard keeps the `c_`, `r_` and candidate `rc_` anchors and the time.

### F7. The ChatGPT citation clean-up leaves garbage or deletes words
- **Severity:** medium
- **Where:** 2.5, 4.2
- **Problem:** (a) The last pass strips only the characters U+E200 to U+E2FF. A marker shaped like the one in 2.5 (`U+E200 cite U+E202 turn0search0 U+E201`) then shows up as the visible text "citeturn0search0" whenever its reference was not matched: an unknown type, a missing `matched_text`, or text that differs. (b) "Anything else: its alt text when present, else removed." Some markers stand for visible words (ChatGPT uses them for named entities and image groups; verify which ones carry `alt`). Removing those deletes words from the answer without a trace: "met with X in Paris" loses "X". (c) If this is built with `text.replace(matched, alt)`, JavaScript reads `$&`, `$'` and `$1` in the replacement as patterns. An `alt` that contains "$'" pastes the rest of the message in at that point. (d) Matching by text replaces the first occurrence, which may not be the one the reference points to.
- **Suggested fix:** Make the last pass remove whole sequences (U+E200 through the next U+E201). For an unmatched sequence, keep any readable payload, such as an entity's display name, then strip any stray private-use characters. Replace by `start_idx` and `end_idx`, working from the end of the string backwards, after checking that the slice equals `matched_text` (index units: see F10). Use split and join or a replacer function, never a replacement string. Count unmatched markers in the note, and write a fixture for each case.
- **Answer:** Accepted, with facts checked on November 15 across 937 references with `matched_text`. Indexes count code points: where an emoji came before the reference (34 cases), the code-point slice equaled `matched_text` 30 times and the UTF-16 slice 0 times. `alt` coverage by type: present on all `entity` (90), `grouped_webpages` (459), `url` (8) and `image_group` (3); absent on all `file` (131), `sources_footnote` (111), `client_defined_widget` (23), `dil` (5) and `hidden` (101). Rules in 4.2: replace by code-point index from the end backwards after checking the slice; when the slice differs, search for `matched_text` from the end; `file` becomes `[file: name]`; `sources_footnote` feeds the sources list; widgets get the F2 placeholder; `hidden` is removed. Replacements use a replacer function. The last pass removes whole U+E200 to U+E201 sequences, and unmatched markers are counted in the note.

### F8. ChatGPT turns: tool detection, merging and counting
- **Severity:** medium
- **Where:** 4.2, 3.3
- **Problem:** (a) Tool calls are detected by `content_type: code`. An assistant node addressed to a tool (`recipient` other than "all") can also carry `text` content (verify; image generation and canvas calls send JSON). That JSON would print as the assistant's answer. (b) Each assistant and tool node on the path becomes its own Message, so one answer with three searches becomes about seven "## ChatGPT" sections. "N messages" then counts nodes, while for Claude it counts turns. Scenario: 10 prompts, each answered after three web searches. Counted the Claude way that is 20 messages; the ChatGPT export says about 80 and shows about 70 headings. (c) The hidden-message skip runs before the tool mapping. If tool or `thoughts` nodes carry `is_visually_hidden_from_conversation` (verify), the tool steps the spec promises disappear.
- **Suggested fix:** Classify by role and `recipient` first and by `content_type` second. Merge the consecutive non-user nodes between two user messages into one assistant Message with ordered blocks. Define "messages" as user turns plus assistant turns on every platform, and use that same definition in the live count comparison. Have the probe report hidden-flag counts per content type.
- **Answer:** Accepted; the data confirms both concerns (November 15, 22 chats). 260 assistant nodes addressed to a tool carry `text` content, so classification goes by role and `recipient` first. The hidden flag sits on 48 `tool` multimodal outputs, 30 `tool` text outputs, 2 assistant text nodes and 1 `thoughts` node, so skipping hidden nodes would drop tool steps. Spec v2 4.2: hidden tool and thinking nodes are kept with a "hidden in ChatGPT" label; only `system` nodes are skipped. Non-user nodes between two user messages merge into one assistant Message with ordered blocks. "Messages" means user turns plus assistant turns on every platform (3.3).

### F9. The spec never says how each adapter gets the conversation id and account context
- **Severity:** medium
- **Where:** 3.6, 4.1, 4.2, 4.4
- **Problem:** The spec never says how each adapter gets the conversation id or the account context, or what counts as a "conversation page" (3.6). 0.4.0 takes `pathname.split('/')[2]`. Scenario 1: ChatGPT project and custom GPT chats live at `/g/{gpt-or-project}/c/{id}`. Slot 2 holds the GPT id, so the fetch returns 404 and the export falls back. Scenario 2: ChatGPT Team, Business and Enterprise workspaces likely need a workspace account header (`ChatGPT-Account-Id`), and without it the conversation is not found (verify on a workspace account; the check covered one personal account). Scenario 3: a content script can read cookies only through `document.cookie`. If `lastActiveOrg` is HttpOnly (verify), Claude falls back to "the first org with chat". For a user with two chat orgs, such as personal plus Team, that can be the wrong one: 404, then about 4 turns from the page. Gemini paths: see F5.
- **Suggested fix:** Give each platform a small `conversationRef(location)` that returns the id plus its context, with unit tests over each URL form. ChatGPT: take the id after `/c/`, and send the workspace header when the session or a cookie names one. Claude: on a 403 or 404, try the other chat-capable orgs before falling back.
- **Answer:** Accepted. Each platform gets `conversationRef(location)` with unit tests over every URL form (4, intro). ChatGPT takes the id after `/c/`. Claude: `lastActiveOrg` is readable through `document.cookie` (checked November 15), and a 403 or 404 tries the other chat-capable orgs before failing. The ChatGPT workspace header is unverified (no workspace account available): a 404 on a workspace account reports the reason, and the case is in the untested list.

### F10. Claude citation offsets: units and insertion order
- **Severity:** medium
- **Where:** 4.1, 8
- **Problem:** Putting a marker at `end_index` assumes the index counts JavaScript UTF-16 code units. A Python backend usually counts code points. Scenario: in "🚀 Launches rose 20% in 2025", with a citation ending after "2025", each emoji before the citation moves the marker one place left, so it lands inside the word ("202[1]5"). An offset that falls between the two halves of an emoji produces invalid text. Inserting front to back also shifts every later index. And a range can end inside a Markdown construct such as link text, inline code or a table cell, where a marker breaks the Markdown. ChatGPT's `start_idx` and `end_idx` raise the same unit question.
- **Suggested fix:** Check the unit on one live message that has an emoji before a citation, and convert with `Array.from(text)` if the indexes count code points. Insert from the highest index down. If an index lands inside a word or a code span, move the marker to the end of that word or span. Add fixtures with emoji and other characters outside the basic plane.
- **Answer:** Accepted. ChatGPT counts code points (see F7). Claude could not be checked: none of 61 chats had a non-BMP character before a citation. Spec v2 treats Claude indexes as code points too, inserts from the highest index down, moves a marker that lands inside a word or a code span to its end, and adds fixtures with characters outside the basic plane. The probe flags the first live Claude case so the unit can be confirmed.

### F11. Claude tool pairing: unpaired calls and results in other messages
- **Severity:** medium
- **Where:** 2.4, 2.5, 4.1
- **Problem:** The counts in 2.4 (7,605 `tool_use`, 7,604 `tool_result`) already show at least one call with no result. The spec does not say how an unpaired call or an orphan result renders. It also implies pairing within one message. For client-side tools, such as the remote-device chats in 2.5, results may arrive in a separate human-role message (verify). That message would render as an empty "## You" turn, the call would show no output, and each such message adds 1 to the count.
- **Suggested fix:** Pair by `tool_use_id` across the whole active branch. An unpaired call renders with "(no result recorded)". An orphan result renders alone with its id. A human message whose only blocks are tool results is folded into the assistant message before it and not counted as a user turn.
- **Answer:** Accepted. Checked November 15 on 60 chats: no tool result sat in a different message from its call, no orphan results, no human message holding only tool results, and 1 call with no result. The rules go in anyway: pair by `tool_use_id` across the active branch, an unpaired call shows "(no result recorded)", an orphan result renders alone, and a human message holding only tool results folds into the assistant message before it.

### F12. The format of tool output is undefined, including inline base64 images
- **Severity:** medium
- **Where:** 3.5, 4.1, 4.2
- **Problem:** "Nothing is trimmed" plus "its input and its output" leaves open what the output looks like. A Claude tool result is an array of blocks (text, image, others), `structured_content` is JSON, and `display_content` is a display format. Scenario: a Claude in Chrome or computer-use chat with 200 screenshots in its tool results. If image parts are stringified, the Markdown holds tens of MB of base64 (verify whether the API returns base64 or file references here), and the Copy result cannot be pasted anywhere useful. ChatGPT `execution_output` with charts, and image-generation tool messages, raise the same question.
- **Suggested fix:** Add a rule to 3.5. Text parts are written as text inside fences. Image parts become image FileRefs (a file in the ZIP, a named line in Copy and Download) and are never written as inline base64. Other structured parts are pretty-printed JSON in a fence. `display_content` is used only when nothing else exists. The input is pretty-printed JSON.
- **Answer:** Accepted. Checked November 15: Claude tool-result image parts are file references (`file_uuid`, `preview_url`, `thumbnail_url`; 397 of them), not base64. Other part types seen: `text` (10,433), `knowledge` (4,388 web results with `title` and `url`), `local_resource` (115 delivered files with `name` and `file_path`) and `image_gallery` (9, with image and page links). Spec v2 3.5 adds the output rule: text parts as fenced text, `knowledge` as a link list, images as FileRefs, gallery entries as plain links, other structured parts as pretty-printed JSON, `display_content` only when nothing else exists, input as pretty-printed JSON. Inline base64 is never written.

### F13. Pasted text attachments are missing from Copy and Download
- **Severity:** medium
- **Where:** 3.5, 4.1
- **Problem:** Claude turns long pastes into attachments with `extracted_content`. Section 4.1 saves them as files in `uploads/`, and 3.5 says Copy and Download show only "a line naming the file". Scenario: the user pastes a 4,000-word draft and asks for edits. Copy gives the request and the edits but not the draft. That text is already in the conversation data and needs no fetch, it is often the most important input, and leaving it out breaks the "nothing is trimmed" rule.
- **Suggested fix:** Inline `extracted_content` in all three formats, as a fenced block under the user message with the file name, and also save it to `uploads/` in the ZIP. Do the same on any platform that returns the extracted text of an upload.
- **Answer:** Accepted as written. `extracted_content` is inlined under the user message in all three formats, fenced and named, and also saved to `uploads/` in the ZIP.

### F14. Claude artifact replay and the file merge key
- **Severity:** medium
- **Where:** 4.1
- **Problem:** (a) "`create`, `update`, `rewrite` with `content`": older `update` commands carry `old_str` and `new_str`, not `content` (verify on the data). Treating an update as a whole replacement writes a fragment out as the final file. Applying an update whose `old_str` is not found (the update also failed on screen) drifts away from the real artifact without a note. (b) Replay must use only the active branch; replaying every node in the tree applies edits from abandoned branches. (c) `wiggle/list-files` gives paths, while message `files` give uuids and names. "Merged by path" has no shared key, so the same file can be fetched twice and land as `report.docx` and `report-2.docx`.
- **Suggested fix:** Replay `create` and `rewrite` as a replace. Replay `update` as a single string replace, with a note when `old_str` is missing. Use active-branch messages only. Merge on uuid where both sides have it, otherwise on file name plus size, and when unsure keep both copies with a note.
- **Answer:** Accepted. In 60 chats the `artifacts` tool showed 22 `create` and 1 `read`, no `update`, so the update shape stays unverified. Replay rules in 4.1: `create` and `rewrite` replace; `update` applies `old_str` to `new_str` once, with a note when `old_str` is missing or the shape differs; active-branch messages only. File merge: uuid where both sides have one, else name plus size, else keep both with a note.

### F15. ZIP names: collisions overwrite files and links break
- **Severity:** medium
- **Where:** 3.5, 7
- **Problem:** (a) 0.4.0's `deduplicateFilenames` renames a repeat to `name-2.ext` without checking that the name is free. Files `a.txt`, `a.txt` and `a-2.txt` give two entries named `a-2.txt`, and JSZip's `file()` silently replaces the first. The spec's "duplicates numbered" does not rule this out. (b) `Report.pdf` and `report.pdf` are different entries in the ZIP but collide on the default macOS and Windows file systems when extracted. (c) Names with `: * ? " < > |`, trailing dots or spaces, or reserved names such as `CON` and `NUL` fail to extract on Windows. (d) `[Q3 report (final).pdf](uploads/Q3 report (final).pdf)` is not a valid Markdown link, because the space ends the link target, and most viewers show it as plain text. (e) A length cap that counts characters can split a multi-byte character or cut off the extension.
- **Suggested fix:** Write one `safeName` function. It strips control characters and the Windows set, trims trailing dots and spaces, prefixes reserved names, caps the name at about 100 UTF-8 bytes while keeping the extension, then dedupes case-insensitively against the names already used in that folder, looping until it finds a free one. Write link targets as `<uploads/...>` or percent-encoded. Write one unit test per case.
- **Answer:** Accepted as written. One `safeName` function per spec v2 section 7, with a unit test per case. Link targets use angle brackets (`<uploads/Q3 report (final).pdf>`).

### F16. Copilot collection: stop rule, duplicates, hidden tabs, set size
- **Severity:** medium
- **Where:** 4.5, 3.7
- **Problem:** (a) "Until the top stops changing": a slow load looks the same as reaching the top. The export then honestly says 14 of 26, but a retry would have got everything. The positions already say when to stop. (b) Unlabeled messages have no key. One that stays visible across three scroll steps is collected three times, and the export reports 28 of 26. (c) If the user switches tabs during collection (likely on a long chat, or when it was started from the popup), Chrome throttles timers and stops animation frames in the hidden tab. A virtualized list often draws nothing new in that state, so the time cap ends the run with a partial export. (d) `aria-setsize` as the chat's total was confirmed only on 26- and 18-message chats. On a long chat it may count only the loaded part and grow as you scroll.
- **Suggested fix:** Stop when positions 1 to setsize are all collected, or when a cap is hit. Key unlabeled messages by role, normalized text and the neighboring position. On `visibilitychange` to hidden, pause and tell the user. Keep the largest setsize seen and note it if it changed. Verify on a chat of 100 or more messages.
- **Answer:** Accepted. Stop when positions 1 to setsize are all collected or a cap is hit. Unlabeled messages are keyed by role, normalized text and neighboring position. Collection pauses on `visibilitychange` to hidden and tells the user. The largest setsize seen is kept and a change is noted. No chat of 100 or more messages exists on either account (largest: 26), so that case goes in the untested list.

### F17. Consumer Copilot is a different app from M365 Copilot
- **Severity:** medium
- **Where:** 2.1, 4.5, 6
- **Problem:** 0.4.0 uses different selectors for consumer Copilot (`[data-testid="ai-message"]`) and for M365 (`div.fai-CopilotMessage`), so the two are separate apps. The spec ships copilot.com "behind the same adapter if it uses the same app" and lists it as untested. For a personal user on copilot.com the adapter will likely match nothing, which gives either 0 messages or a format error. A store listing that names a platform and calls it untested invites bad reviews.
- **Suggested fix:** Probe copilot.com while signed in with a personal Microsoft account before deciding (a separate browser profile avoids the work redirect). Until then, leave it out of the listing and the manifest (see F19). Its app may have its own data source, which was not probed and could be simpler than scrolling.
- **Answer:** Accepted. Consumer Copilot leaves 1.0. `copilot.microsoft.com` is removed from the manifest (it redirects away, so the content script never runs there), and `copilot.com` is not added. Probing it needs a Chrome profile signed into a personal Microsoft account; that is Nikhil's call (spec v2 11).

### F18. Popup and clipboard mechanics have gaps
- **Severity:** medium
- **Where:** 3.6, 3.7
- **Problem:** (a) Chrome does not inject declared content scripts into tabs that were open before an install or update. After 1.0 arrives, every Claude or ChatGPT tab that is already open answers the popup with "Receiving end does not exist". (b) A popup closes when it loses focus, and its code stops running. A Copy that takes a while (Copilot scrolling, a large Claude chat) is lost if the user clicks the page, for example on the in-page Cancel button that 3.7 relies on. (c) An in-page Copy after a long collection calls `writeText` when the page may have lost focus (the user switched tabs). That call throws "Document is not focused", and the spec has no retry path.
- **Suggested fix:** When the popup finds no content script, it shows "Reload this tab to use Copier", or it injects the scripts with `scripting` and `activeTab` (see F19). Copy from the popup shows its own progress and Cancel, so the popup is the only control during that run. Everywhere: if a clipboard write fails, keep the text and show a toast with a Copy button, since a fresh click gives both focus and user activation. Write the popup message protocol (actions, result, error text) into the spec.
- **Answer:** Accepted. The popup injects the scripts with `scripting` under `activeTab` when the tab does not answer, after checking the URL is a supported conversation page. That covers tabs open before the update and `copilot.cloud.microsoft`. If the popup closes mid-run, the content script finishes and shows a toast with a Copy button. Any failed clipboard write does the same. The message protocol is written into 3.6.

### F19. Every existing user re-approves Copier to gain two hosts of little value
- **Severity:** medium
- **Where:** 6, 12, 13 (risk 6)
- **Problem:** Adding `copilot.com` and `copilot.cloud.microsoft` turns Copier off for every existing user until they approve the new sites, including users who never open Copilot. Many will not notice, or will not turn it back on. The gain is one host that serves the same app as the already-covered `m365.cloud.microsoft`, plus one host that is untested (F17).
- **Suggested fix:** Three options that avoid forcing re-approval on everyone: (1) Ship 1.0 without new hosts; M365 users already work on `m365.cloud.microsoft`. (2) Add `activeTab` and `scripting`, neither of which shows a warning per Chrome's permission list, and have the popup inject the content scripts into a Copilot tab when clicked. Those two hosts get no in-page buttons, but nobody has to re-approve. (3) Declare the hosts in `optional_host_permissions` and request them from the popup. Option 1 or 2 is the simplest. Confirm the result with the Update Testing Tool either way.
- **Answer:** Accepted, option 2. No host is added to `content_scripts`, so existing users are not asked to re-approve. `activeTab` and `scripting` give popup-only support on `copilot.cloud.microsoft`. Hosts are only removed (`www.google.com`, `copilot.microsoft.com`), which narrows access. The Update Testing Tool confirms no disable before upload.

### F20. Page-reading fallbacks are unspecified and worth little; cut most of them
- **Severity:** medium
- **Where:** 3.1, 3.3, 4 (intro), 13 (risk 2)
- **Problem:** Every platform gets a page fallback, but only Gemini's is specified. 0.4.0's page readers for ChatGPT, Grok, Gemini and Copilot already fail. On Claude and ChatGPT the page holds 1 to 4 turns of a long chat, so a fallback export is a fragment. Five page readers on top of five data adapters roughly doubles the code that breaks when a site changes, for an output the user rarely wants.
- **Suggested fix:** Cut the page fallback for Claude, ChatGPT and Grok. When the data cannot be read, say so ("Could not read ChatGPT's conversation data: HTTP 401. Nothing was copied."). If the owner wants a partial option, make it an explicit "Copy what is on screen" rather than an automatic fallback. Keep Gemini's scroll fallback only if it turns out cheap. Copilot is page reading by design, which is also the only place Turndown is then needed.
- **Answer:** Accepted. Page fallbacks are cut for Claude, ChatGPT, Grok and Gemini. When the data cannot be read, the export stops and says why ("Could not read ChatGPT's conversation data: HTTP 401. Nothing was copied."). Copilot stays page-based by design, and Turndown serves only Copilot.

### F21. The unit tests, as described, cannot run
- **Severity:** medium
- **Where:** 4 (intro), 5, 8
- **Problem:** (a) Files that register on a shared object in the content-script world have no `window` and no exports when loaded in Node. The spec does not say how the tests load them. (b) Copilot conversion needs a DOM. The vendored browser build of Turndown uses `document` and `DOMParser`, so "no new dependency" means the converter goes untested. (c) `FileRef.fetch()` puts a closure holding org ids or tokens inside the parse result, so parse is not pure data in, data out. (d) Synthetic fixtures written from the author's reading of the data only prove that the parser matches the author's own assumptions.
- **Suggested fix:** End each file with `globalThis.Recurate = Object.assign(globalThis.Recurate || {}, { ... })`, which works both in a content script and in Node (loaded with `vm`, or with a two-line shim). Have the Copilot parse take plain records (`{ pos, setsize, role, html }`), test the dedupe in Node, and either test conversion live only or add a dev-only DOM package and say so. Make FileRef a plain descriptor (for example `{ kind: 'claude-file', uuid }`) that the fetch step resolves. Have the probe save a skeleton of each live response with no values (key paths and types only), and build the fixtures from that, so the field shapes come from the site rather than from memory.
- **Answer:** Accepted. Files end with `globalThis.Recurate = Object.assign(globalThis.Recurate || {}, { ... })` and tests load them with `vm`. The Copilot parse takes plain records (`{ pos, setsize, role, html }`). Turndown conversion is tested live only; no dev dependency is added. FileRef is a plain descriptor resolved by the fetch step. The probe saves a values-free skeleton of each live response (key paths and types), and fixtures are built from it.

### F23. The keyboard shortcuts clash with ChatGPT and Chrome
- **Severity:** medium
- **Where:** 3.6
- **Problem:** Several shortcut guides list Cmd/Ctrl+Shift+C as ChatGPT's own "copy last response" (check ChatGPT's shortcut list with Cmd/Ctrl+/). On Windows and Linux, Ctrl+Shift+C also opens the DevTools element picker, and Cmd/Ctrl+Shift+D is Chrome's "bookmark all tabs". 0.4.0's handler calls `preventDefault` and fires even while the user is typing. Once ChatGPT exports work again in 1.0, pressing Cmd/Ctrl+Shift+C there runs both copies, and whichever writes last wins.
- **Suggested fix:** Drop the in-page key handlers. Add a manifest `commands` entry for `_execute_action`, which opens the popup, needs no permission, and can be rebound at chrome://extensions/shortcuts. If page shortcuts stay, skip them when focus is in an editable field and on sites where they clash.
- **Answer:** Partly confirmed on November 15. ChatGPT's own shortcut list (Cmd+/) has no Cmd/Ctrl+Shift+C, so that clash is out of date. It does list Control+Shift+D as dictation, and 0.4.0's handler fires on Control or Command, so the D clash holds. Accepted fix: the in-page key handlers go; a manifest `commands` entry for `_execute_action` opens the popup, with a suggested Alt+Shift+C that users can rebind at chrome://extensions/shortcuts.

### F24. The security wording overstates, and links in exports can leak
- **Severity:** low
- **Where:** 7
- **Problem:** "No HTML is generated for viewing, so no script can run from an export" is not true of the ZIP. Artifacts and uploads saved as `.html` or `.svg` run their scripts when opened, and raw HTML inside message text renders in some Markdown viewers. Links have two risks. A fallback link to a ChatGPT `download_url` or any other signed URL puts a time-limited credential into a file people share. An image embed (`![](https://...)`) makes the viewer fetch the image whenever the file is opened.
- **Suggested fix:** Reword 7 to "Copier generates no HTML. Files the chat produced are saved as they are." Never write download or signed URLs into an export; write the file name plus "not downloaded". Use plain links, not image embeds, for remote files.
- **Answer:** Accepted. Section 7 now reads "Copier generates no HTML. Files the chat produced are saved as they are." Signed or download URLs are never written into an export; a failed file is its name plus the reason. Remote images are plain links, not embeds.

## Open questions (section 11)

**1. Markdown only?** Agree. The case against HTML is the two vendored libraries and the upkeep of a second writer, more than the XSS surface: the export is the user's own content, opened locally. Before release, three things are worth deciding knowingly. Download on ChatGPT, Grok, Gemini and Copilot changes from `.html` to `.md`. Windows has no default viewer for `.md`, so non-technical users there lose a file they could open with a double click; the "periodic auto-export for non-technical users" item in CURRENT_STATE points the same way. The manifest description and the store listing (including screenshots 2 and 4) sell the HTML export and have to change. If a readable format is wanted later, it can be its own step after 1.0.

**2. Drop Google AI Mode?** Agree. The feature has been shelved since July. The content script runs on every google.com page and shows buttons on ordinary searches, and google.com is the hardest host to justify in review. Removing a host narrows permissions, so it triggers no re-approval. Remove the `google` branches from the code as part of the same change.

**3. Vendor Turndown for Copilot?** Agree, with conditions. A hand-written HTML-to-Markdown converter that handles tables, nested lists and code would cost more to write and maintain than a pinned, MIT-licensed, vendored file. Conditions: (a) check on the live Copilot DOM that tables have header cells, because the GFM plugin leaves tables without a header row as raw HTML; (b) check how Copilot marks up code blocks and citation pills, and add a few Turndown rules to drop UI chrome instead of reusing 0.4.0's `sanitizeHTML`; (c) vendor an exact version with its license header; (d) if F20 is accepted, Turndown serves Copilot (and maybe Gemini's fallback) only, so the "serves every page-reading fallback" argument falls away. Testing it needs a DOM in Node (F21).
